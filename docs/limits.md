# Слабые места и полный план

Короткая версия — [ARCHITECTURE.md](../ARCHITECTURE.md), §6.

## Слабые места

- правила замен — наше допущение (`предложено`), не методика заказчика;
- **117 строк (4,9 %) без категории** — ни одно слово-признак не сработало: составные позиции («Комплект
обеспечения отказоустойчивости в составе:»), услуги и ПО («Подсистема безопасности объектов КИИ»), редкие
классы без категории (геотекстиль, накладки, адаптеры). Для них работает только второй проход по тексту;
- **1 290 из 2 156 товаров (60 %) без извлечённых характеристик:**

  | Причина                                                        | Строк | Пример                                                  |
  | -------------------------------------------------------------- | ----- | ------------------------------------------------------- |
  | у категории в `attributes.yaml` нет характеристик              | 187   | редкие категории                                        |
  | характеристики описаны, экстракторов нет                       | 368   | мастики, приборы, сцепная арматура («Серьга СРС-7-16»)  |
  | экстрактор есть, значения в названии нет или оно в коде модели | 735   | «Силовой кабель для подключения к АКБ», «Зажим СР.2-50» |

  Больше всего пустых: шкаф (прочий) 64, профиль монтажный 62, мастики и краски 59, воздуховоды 57, приборы 53,
  сцепная арматура 53. Такие строки не выпадают из поиска: сравниваются по категории и тексту, по каждой
  характеристике запроса — «? не указано» и штраф 0,05; hard-правило их не отсекает. Сознательно не покрыты в
  прототипе;
- экстракторы покрывают 185 из 334 характеристик; из 113 hard без экстрактора 47 дочитывает модель, **66
hard-правил некому проверить**: кандидат такой категории не бывает «той же», а без подтверждённой hard — только
«не проверено». Известные пробелы: размер в марке (`ОА 150-1`), цветовая температура светильников, напряжения
обмоток трансформатора (берётся первое);
- модель читает только характеристики с рядом значений: без ряда (свободное число) ей не из чего выбирать;
пороги уверенности 0,9 и 0,8 подобраны на этой базе; кэш — файл JSON Lines, при многих загрузчиках нужна таблица;
- в режиме `live` запрос ждёт модель — вектор и до трёх вопросов по очереди: категория, характеристики, судья;
при её недоступности поиск идёт по правилам и написанию (в журнале — предупреждение);
- модель и вектор запроса — через OpenRouter, ключ обязателен; в проде — локальные модели, ключ не нужен;
- судья видит только названия: 10 лучших нерешённых кандидатов, остальные остаются «не проверено»; его
уверенность 0,9 не откалибрована на ответах специалиста;
- категорию модель выбирает из 8 ближайших по написанию и смыслу: если верной среди них нет, не выберет;
- жаргон и порядковые числа («двадцатка», «пятая категория») не читаются ни правилами, ни моделью уверенно;
- поле `написания` в `attributes.yaml` код не использует: как читать характеристику, решает `domain/features.py`,
специалист этого правилом не задаст;
- нет сравнения «в диапазоне»: «муфта 400–1000 мм²» читается как одно число;
- версия знаний — хеш содержимого релиза; правка экстрактора её не меняет, поэтому после неё `positions load`
нужен вручную (Docker делает его при каждом старте);
- редактор знаний: публикация синхронная (проверка ~5 с, разбор истории — дольше) и не атомарна с разбором —
при сбое посередине релиз активен, а строки разобраны старым (`/api/stats` предупредит, `positions load`
доразберёт); проверка влияния читает запросы только правилами; добавлять характеристики, ряды и категории
страница не умеет; выгрузки релиза обратно в yaml нет; `evaluate.py` по-прежнему берёт знания из yaml;
карточки и проверка считают, что история — один файл;
- веса и порог подобраны на 52 запросах того же автора — статистически слабо;
- параметры, зашитые в код модели (`ЗПС-Мл-13,5П/7`), не разбираются; совпадение кода модели пока не даёт
метку «та же»;
- составные позиции («… в составе:») сопоставляются целиком;
- нет пошагового трейса в ответе: видны разбор запроса и разбор каждого кандидата, но не «кто отсеян на каком
шаге»;
- шумовые пометки из `research/noise.yaml` не вычищаются;
- ключ карточки зависит от разбора: запрос, прочитанный иначе (другая версия знаний, `cache` вместо `live`,
модель недоступна), в карточку не попадёт. При публикации из `/knowledge` ключи карточек пересчитываются
и совпавшие сливаются; после `knowledge load` из yaml — пока нет; связи и журнал при этом не теряются (id
строк стабильны при `positions load`);
- правка разбора в выдаче — только значение из ряда справочника: у характеристик без ряда (габариты, «3х2,5+1х1,5»)
его можно лишь снять; правка не запоминается — при пересчёте ключей карточка перечитывает исходный текст
запроса без неё;
- нет авторизации: автор решения — свободное поле; нет очереди просмотра и ручного слияния карточек; отменить
«не подходит» из интерфейса нельзя (строки уже нет в выдаче) — только новым решением через API.
