# Шаги поиска подробно

Короткая версия и схема — [ARCHITECTURE.md](../ARCHITECTURE.md), §1–2. Здесь каждый шаг: **что делает → зачем →
что ловит хорошо → где ошибается → чем настраивается.**

## Заранее, со всей базой

**0. Чтение таблицы.** Строка, наименование, цена. Номер строки — постоянный ключ: перезагрузка не меняет id,
ссылки на решения специалиста не ломаются.

**1. Нормализация.** Нижний регистр, `ё` → `е`, убирает номер пункта в начале (`1.7.2)`), приводит размеры к
одному виду: `7х1,5` / `7*1.5` / `7 × 1,5` / `7 на 1,5` / «семь на полтора» → `7x1.5`. Числа словами переводятся в
цифры только в размере «A на B»: там ясно, что это числа и к чему они относятся; одиночное «два» читает модель
(шаг 4а). Исходная строка хранится для показа.
*Зачем:* одна вещь записана десятком способов — без этого шага тексты не совпадут.
*Плохо:* пометки «(или аналог)», «(прим. …)», обезличенные «Объект-А» пока не вычищаются — они описаны в
`research/noise.yaml`, но в код не перенесены (слабо влияют на оценку: это малая доля текста).
*Настройка:* `domain/knowledge.py: normalize`. Правила консервативные: агрессивная чистка стирает значимое
(букву «Э» в марке кабеля).

**2. Категория.** Что это за вещь: кабель силовой, кабель контрольный, лоток, видеокамера… По словам-признакам
из `categories.yaml`: признак ищется с начала слова, самое раннее совпадение побеждает, при равенстве — более
длинное. Слово-исключение отменяет совпадение («кабель-канал» — не кабель). Категория «(прочее)» уступает
более точной: «труба гофра» — не «труба (прочая)», а «труба гофрированная».
*Зачем:* категория отсекает похожее по тексту, но другое по сути, и говорит, какие характеристики важны.
*Хорошо:* наименования из смет — главное слово обычно в начале. Служебные строки («Перевозка…»,
«Погрузка…») — тоже категории, группа «служебные строки»: они помечаются и никогда не становятся кандидатами.
*Плохо:* составные позиции («Шкаф … в составе: коммутатор, ИБП») получают категорию по первому слову.
117 строк (4,9 %) без категории — для них работает только текстовый второй проход.
*Настройка:* `research/categories.yaml`. Словарь собран не только по этой базе, но и по отраслевым
справочникам: поэтому система узнаёт «огнетушитель», которого в базе нет, и честно говорит «таких позиций нет».

**3. Характеристики.** Достаёт параметры из названия по схеме категории: у кабеля `7x1.5` — 7 жил по 1,5 мм²,
`нг(А)-FRLS` — исполнение, «Э» в марке — экран; у ворот `2250х6000` — габарит без порядка сторон; у трубы —
диаметр (`d=25 мм`, `Ду25`); у лотка `100х400` — ширина 400 и борт 100. Единицы переводятся к одной
(`0,4 кВ` = `400 В`; `кВА` и `кВт` — разные величины и не смешиваются).
*Зачем:* «параметры решают» — кабель 7×1,5 и 7×2,5 по тексту почти одинаковы, а по сути разные.
*Хорошо:* стандартные записи с единицами и марки кабеля.
*Плохо:* параметры, зашитые в код модели (`ЗПС-Мл-13,5П/7`, `ОА 150-1`); экстракторы есть для 185 из 334
характеристик (из 257 hard без экстрактора 113 — `/api/stats`, тест не даёт числу расти), у 937 из 2 381 строк
извлечена хотя бы одна (с моделью, шаг 3а, — у 1 142). Составные формулы не читаются, а **отклоняются**: «3х2,5+1х1,5» — не 3 и не 4 жилы, и
запрос с такой формулой не считается «молчащим» о сечении (см. метку «не проверено» в шаге 8). Принцип: **не уверен — не извлекай.** «6А» у автомата — ток, а не
отключающая способность 0,006 кА; «гофра 32» без «мм» не читается как диаметр. Ложная характеристика хуже
пропущенной: пропущенная даёт «? не указано, проверьте», ложная — неверный отказ.
*Настройка:* какие характеристики у категории и их единицы — `attributes.yaml`; как читать — `domain/features.py`
(общие по единице, по коду характеристики, по категории и по ряду значений из yaml).

**3а. Что не прочитали правила — спрашивается у модели.** Только hard-характеристики с рядом значений в
`attributes.yaml` (47 из 113 hard без экстрактора): толщина стали воздуховода, марка провода АС/А/СИП, материал
наконечника. Модель (Jev Choice через OpenRouter) не пишет значение, а **выбирает вариант**: значения ряда,
«указано значение не из списка» или «не указано» — поэтому размер, которого специалист не перечислил, она
выдумать не может. Выбор принимается кодом, только если выбранное число есть в строке, цифрами или словами
(«0,5 мм» → 0,5 проходит, 0,7 для той же строки — нет; единицы переводятся), и уверенность ≥ 0,8. Найденное в
строке число — вторая, независимая проверка, поэтому от модели нужна меньшая уверенность, чем для значения-слова
(«медь» по марке ТМЛ): его сверить не с чем, порог 0,9. Из 105 ответов с уверенностью 0,8–0,9 и числом в строке
просмотренные почти все верны (размеры лотков, резьба, число жил); сомнительный — ток розетки из «10/42».
Что делает ответ:


| Ответ модели                                      | Что значит для поиска                                                                          |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| уверенно выбрано значение, проверка пройдена      | характеристика сравнивается, как прочитанная правилом; в UI — значок «ИИ»                      |
| уверенно «не указано»                             | запрос о ней молчит, как без модели                                                            |
| уверенно «не из списка» или значения нет в строке | указана, но не прочитана: найденное по ней не подтверждается («толщина 3 мм» — «не проверено») |
| неуверенно, сбой, нет в кэше                      | ничего не добавляет: как без модели                                                            |


*Зачем:* так сомневающаяся или недоступная модель никогда не делает хуже правил — это проверено на регрессии:
первая версия считала неуверенный ответ «указанным», и hit@1 упал до 0,85.
*Пороги* — `llm_min_confidence` (0,9) и `llm_min_confidence_stated` (0,8) в настройках.
*Режимы* (`ANALOG_LLM`): сервис работает в `live` (по умолчанию `auto` = `live` при заданном
`OPENROUTER_API_KEY`, ключ обязателен) — недостающие ответы спрашиваются у модели и дописываются в кэш
`data/llm/readings.jsonl`. `cache` (только кэш) и `off` (только правила) — для воспроизводимой оценки и тестов.
Ключ кэша — модель, строка, вопрос и его варианты: правка ряда в yaml — новый вопрос, старый ответ не переиспользуется.
*Цена:* вся база — ~1 100 запросов к модели, ~$0,04, один раз; повторная загрузка спрашивает только новое.

**4. Хранение.** Строка, категория, характеристики (JSON), нормализованный текст с триграммным индексом
`pg_trgm` и **версия знаний**, которой она разобрана. Знания живут в БД релизами (`knowledge_releases`, одна
активная); версия = номер + хеш содержимого, поэтому правка — новая версия. `research/*.yaml` только наполняет
пустую БД (`knowledge load` — явный импорт); дальше знания правит специалист (шаг 11). `/api/stats`
предупреждает, если база разобрана старой версией («выполните `positions load`»).
Для товарных строк — ещё **вектор названия** (`position_embeddings`, pgvector, 1024 числа): модель `baai/bge-m3`,
в прототипе через OpenRouter, в проде — та же открытая модель локально рядом с сервисом (меняется один класс,
`OpenRouterEmbedder`). Векторы считаются один раз при загрузке (2 273 строки) и кэшируются в
`data/llm/embeddings.jsonl` (~25 МБ, не в git) и лежат в дампе базы. Вектор запроса считается при каждом запросе — поэтому ключ обязателен.

## На каждый запрос

**1. Проверка входа.** Пустой запрос, одни цифры или знаки, длиннее 500 символов → понятное сообщение и HTTP 400,
а не сбой. Неожиданная ошибка → 500 с `trace_id`, по которому её найти в журнале; детали наружу не уходят.

**2–4. Нормализация, категория, характеристики** — те же функции, что для базы. Запрос и строки базы приводятся
к одной структуре, дальше сравниваются структуры, а не строки.

**1б. Опечатки — подсказкой при вводе, не молча.** Слова-признаки категории ищутся с начала слова, поэтому
«кабль контрольный» категорию не находит, а «rf,tkm» (английская раскладка) не находит ничего. Пока запрос
набирается, `GET /api/suggest` предлагает: запрос с исправленными словами; последнее слово дописанным
(`domain/completion.py`: из слов истории, начинающихся с набранного, — те, что в названиях идут после предыдущего
слова, чаще всего — «кабель конт» → «кабель контрольный»); категории, которые запрос называет или начинает, —
выбор фиксирует категорию так же, как исправление в блоке «Что система поняла»; наименования истории по доле
триграмм запроса, которую они содержат (длинное название не штрафуется), начинающиеся с запроса — первыми. После
поиска с опечаткой — строка «Возможно, вы имели в виду». Словарь — слова названий истории и
справочника (`domain/spelling.py`): незнакомое слово заменяется знакомым в одной-двух правках
(Дамерау–Левенштейн, при равенстве — частое) или им же в русской раскладке. Слово знакомо в любой форме
(«порошковый» при «порошковая» в базе — сравниваются основы), марки и размеры с цифрами, короткие слова и
недописанное последнее слово не трогаются. Исправление не применяется само: без справочника марок «Legrand» и
опечатка неотличимы, решает человек.

**4б. Разбор показан как категория интернет-магазина, и его можно поправить.** Блок «Что система поняла»:
хлебные крошки «группа › категория» и прочитанные значения чипами, как выбранные фильтры; не указанные жёсткие —
одним чипом «уточнить N». По «изменить» раскрываются все характеристики категории — сначала указанные
в запросе (значение, жёсткая / мягкая, кто прочитал: правила, «ИИ» или «вы»), затем «можно указать»: не
указанные, с вариантами из ряда справочника; жёсткая не указанная помечена «уточнить» — по ней подойдёт любое
значение. Специалист меняет категорию (список всех категорий по группам), выбирает значение из ряда или
снимает прочитанное («не указано») — запрос перечитывается с правкой поверх (`correction` в `POST /api/search`),
поиск повторяется. Значение выбирается только из ряда и только если экстрактор принимает его как своё
(`FeatureExtractor.accepts`): выбранное сравнивается со строками базы так же, как прочитанное. Отметки
«та же / аналог» уходят с той же правкой — в карточку исправленной структуры: «кабель контрольный 7 жил» с
выбранным 1,5 мм² — та же карточка, что «кабель контрольный 7х1,5». Правка разбора действует на один запрос;
если ошибка в правилах — ссылка «Правила категории →» ведёт на `/knowledge` с этой категорией (шаг 11).

Но запрос пишут **своими словами**: с опечатками, без марки, числами словами — «кабел контрольный семь жил по
1,5», «автомат легранд двухполюсный 6 ампер», «трансформатр сухой 1250ква». Строки базы так не пишут, поэтому
для запроса модель спрашивают о большем:

**2а. Вектор запроса.** Запрос один раз переводится в вектор (bge-m3) — он нужен дважды: для выбора категории
(3б) и для отбора кандидатов по смыслу (5). Модель недоступна — вектора нет, оба шага идут по написанию.

**3б. Категория — если не сработало ни одно слово-признак.** Код выбирает 8 ближайших категорий, через одну из двух
списков: **по написанию** — чьё название, признак или синоним больше всего содержится в запросе по триграммам
(«трансформатр» делит с «трансформатор силовой» бо́льшую часть) — и **по смыслу** — косинус вектора запроса и
вектора описания категории «название: признаки, синонимы» («бесперебойник» → ИБП, «фонарь для улицы» →
светильник). Модель выбирает одну из 8 или «ни одна не подходит». Принимается при уверенности ≥ 0,9, иначе —
поиск без категории, как без модели. Модель не называет категорию сама: только из справочника.
*Хорошо:* опечатки, разговорные слова и синонимы без общих букв.
*Плохо:* если верной категории нет и среди 8 ближайших, модель её не выберет; «насос», «болгарка» — категорий
нет, и модель честно отвечает «ни одна».

**4а. Характеристики — и hard, и soft.** Строку базы модель читает только по hard (они отсекают), запрос — ещё и по
soft (они упорядочивают то, что прошло hard): «тридцать ватт» у светильника. Проверка та же, что в шаге 3а:
число должно быть в запросе — цифрами или словами («семь» → 7, «два с половиной» → 2,5, «двухполюсный» → 2).

**5. Кандидаты.** Объединение трёх списков:

- все строки категории запроса — категория до нескольких сотен строк, лимит не нужен: нужная строка не
потеряется из-за непохожего текста;
- 20 ближайших строк **всей базы по написанию** (`pg_trgm.similarity`, доля общих трёхбуквенных фрагментов);
- 20 ближайших строк **всей базы по смыслу** (pgvector, косинус векторов; индекса ANN нет — при 2 тыс. строк
полный перебор быстрее).

Чужие строки нужны, когда правила ошиблись в категории строки («Кабель … в составе», «Трубы гибкие …»), и когда
категория запроса не распознана — тогда кандидаты только они.
Сходство текста для оценки — большее из двух: по написанию и по смыслу, пересчитанному от 0,5 до 1
(`meaning_floor`): у bge-m3 косинус несвязанных названий — 0,3–0,4, связанных — от 0,5.
*Хорошо:* марки и коды, опечатки (`КВВГнг` ↔ `КВВГЭнг`) — написание; синонимы без общих букв («ИБП» и
«источник бесперебойного питания») — смысл.
*Плохо:* по смыслу близки и разные вещи одного рода (7×1,5 и 7×2,5 — почти один вектор) — поэтому смысл только
отбирает и упорядочивает, а решают характеристики (шаги 6–7).

**6. Сравнение характеристик.** Каждая характеристика запроса сравнивается с кандидатом по своему типу из
`attributes.yaml`:


| Тип сравнения | Пример                                                      | Логика                                                            |
| ------------- | ----------------------------------------------------------- | ----------------------------------------------------------------- |
| равно         | сечение, число жил, диаметр                                 | только точно                                                      |
| не хуже       | степень защиты IP                                           | IP65 вместо IP54 — можно (каждая цифра не меньше), наоборот — нет |
| не больше     | SDR трубы                                                   | меньший SDR (толще стенка) заменяет больший                       |
| ступень ± N   | разрешение камеры 1 / 2 / 4 / 8 Мп; мощность трансформатора | ±1 ступень по умолчанию, у мощности допуск 0                      |
| включает      | исполнение кабеля                                           | нг(А)-FRLS заменяет нг-LS, нг-LS не заменяет FRLS                 |
| без порядка   | габариты                                                    | 2250×6000 = 6000×2250                                             |


Итог по характеристике: ✓ совпало, ↑ не хуже (выполнено, но не то же), ~ мягкое отличие, ? у кандидата не
указано (не ошибка, а «проверьте»), ✗ нарушено.

**Строка чужой категории** проверяется правилами **категории запроса**: её название заново читается
экстракторами запроса («Кабель ВВГ 5х95», отнесённый правилами к другому, всё равно даёт 5 жил по 95 мм²).
Нарушена hard — отсеяна, как своя; не нарушена — не выше «не проверено»: что это та же вещь, правила не
подтвердили. В UI такая строка помечена.

**7. Правила специалиста.** Нарушена hard-характеристика — кандидат исключается. Soft отличается — штраф и
пометка. Info — только показывается.
*Зачем:* какие замены допустимы, знает специалист; правило работает на всей базе без правки кода.
Фрагмент `attributes.yaml` (кабель контрольный):

```yaml
- характеристика: "сечение_жилы"
  единица: "мм²"
  ряд: [0.75, 1, 1.5, 2.5, 4, 6, 10]
  уровень: hard
  сравнение: равно
  замена: "только точно"
  источник: "ГОСТ 22483 (ряд номинальных сечений жил); каталоги производителей"
```

У каждой характеристики есть **происхождение** (ГОСТ / каталог / здравый смысл / догадка) и статус
(`предложено` → `утверждено`). Все правила прототипа — `предложено`: это наше допущение, показывающее формат и
механизм; методику замен утверждает специалист заказчика (вопросы к нему — `research/questions_for_specialist.md`).

**8. Оценка.** Число 0…1 для сортировки и порога, из частей, которые UI показывает как есть:

```
оценка = 0,35 · сходство текста (большее из: по написанию, по смыслу)
       + 0,45 · доля выполненных характеристик запроса (soft весит половину hard;
                выполнена с запасом — IP65 вместо IP54, 33 Вт вместо 30 — весит 0,75 точной)
       + 0,20 · та же категория
       − 0,10 за каждое мягкое отличие − 0,05 за каждую hard, не указанную у кандидата
```

Если в запросе нет ни одной характеристики, вклад «характеристик» — половина (0,225): решают категория и текст.
Запас учитывается, чтобы из двух подходящих выше стоял тот, что ближе к запрошенному: «светильник 30 Вт IP54»
без этого ставил первым 33 Вт IP65 — у него текст чуть ближе.
Метка:


| Метка             | Когда                                                                                                                                                                      |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **та же позиция** | каждая hard категории прочитана у обоих и совпала точно; запрос не умалчивает о hard, которую кандидат указывает                                                           |
| **аналог**        | hard не нарушены и хотя бы одна hard подтверждена; остальное отличается, лучше или не указано                                                                              |
| **не проверено**  | hard не нарушены, но ни одна не подтверждена, или запрос указывает hard в нечитаемом виде (формула «3х2,5+1х1,5»; модель уверена, что значение указано, но его нет в ряду) |
| **по тексту**     | категория запроса не распознана, правила не применялись                                                                                                                    |


Метки «не проверено» и «по тексту» — то, что правила не решили; их разбирает судья (шаг 9а).

«Не проверено» появилось после проверки сечений на реальных строках: «ТМЛ 50» без такого наконечника в базе
выдавал ТМЛ 35/120/185 как аналоги — размер в марке не читался, похож был только текст (теперь марку
`ТМЛ 50-10` читает правило, и такой запрос — честный `hard_mismatch`). Неподтверждённое
совпадение показывается, но не называется найденным. Порядок: «те же», аналоги, по тексту, не проверено;
внутри — по оценке.
*Настройка:* `config/search.yaml`, без правки кода.

**9. Порог и «не найдено».** Выше порога 0,5 — до 5 результатов. Никого — **«не найдено»** с одной из причин и
ближайшей строкой; если выше порога только «не проверено» — эти строки и причина `unverified` вместе:


| Причина            | Когда                                                                                | Пример                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `category_absent`  | категория известна, в истории её нет                                                 | «огнетушитель порошковый ОП-5» — огнетушителей в базе нет                                                      |
| `hard_mismatch`    | строки категории есть, все нарушают hard                                             | «трансформатор сухой 1000 кВА» — ближайший ТСЗ-1250: мощность 1250 вместо 1000                                 |
| `low_score`        | правила выполнены, но характеристики не указаны и текст далёк                        | —                                                                                                              |
| `unverified`       | похожие есть, но ни одну hard не удалось сравнить; в карточке — что проверить руками | «Кабель ВВГнг(А)-LS 3х2,5+1х1,5» — ближайший 3х2,5, формула не сравнена                                        |
| `dismissed`        | правила похожие пропустили, но судья (9а) уверенно счёл каждую другим товаром        | «Воздуховод оцинкованный d=200 толщина 3 мм» — толщину 3 мм правила сравнить не смогли, судья отверг найденные |
| `unknown_category` | категория не распознана, по тексту ничего выше порога                                | «насос циркуляционный Grundfos»                                                                                |


Пять случайных строк система не показывает никогда. Без категории запроса кандидаты — ближайшие по всей базе, с
тем же порогом (без категории и характеристик оценка ниже, поэтому проходит только очень близкий текст). Если
категория известна, но строк в ней нет — ближайшая строка показывается как пояснение, не как ответ.

**9а. Судья — что правила не решили.** Кандидаты выше порога с меткой «не проверено» или «по тексту», 10 лучших,
одним запросом показываются модели с текстом запроса и категорией; на каждого она выбирает: та же позиция /
аналог / не подходит / «по названиям нельзя понять». Принимается уверенность ≥ 0,9. Границы задаёт код:

- отсеянное hard-правилом модель **не видит вовсе** — переспорить «7×2,5 ≠ 7×1,5» она не может;
- «не подходит» — кандидат убирается из выдачи (если убраны все — причина `dismissed`);
- «аналог» или «та же» делает «не проверено» аналогом; «той же» строка становится, только если это строка
категории запроса и все её сравненные характеристики совпали точно; строка чужой категории — не выше аналога;
- «по тексту» (категории нет) так и остаётся, вердикт только показывается;
- неуверенный ответ, «нельзя понять», сбой — кандидат остаётся, как его оставили правила.

*Зачем:* «не проверено» честно, но бесполезно покупателю; модель по двум названиям часто видит то, чего нет в
yaml (толщина, назначение, комплект). *Цена:* ещё один запрос к модели — только когда правила не решили.

**10. Подтверждение специалистом и золотые карточки.** У каждого кандидата — кнопки «та же позиция», «аналог»,
«не подходит», «пропустить» (`POST /api/decisions`). Решение уходит не к тексту запроса, а к его **структуре**:
ключ карточки — категория и прочитанные характеристики (`kabel_kontrolnyy|{"сечение_жилы": 1.5, "число_жил": 7, …}`);
у запроса, из которого ничего не прочитано, — нормализованный текст. Поэтому «кабель КВВГнг-LS 7*1.5» и «Кабель
контрольный КВВГнг-LS 7х1,5 мм2» — одна карточка, а «ИБП 12В для улицы» и «бесперебойник 12 вольт уличный»
сходятся, если модель прочитала второй запрос (в живом режиме сходятся).

Карточка — **типовая позиция**: связи со строками истории «та же» / «аналог» / «не подходит» и журнал всех
решений (`decisions`, только дописывается; в связи — последнее решение по паре). На следующий запрос той же
структуры (шаги 6–9):

- подтверждённая строка идёт первой с меткой «подтвердил специалист»; если поиск её не достал — подтягивается
по id; судье она не показывается;
- решение специалиста сильнее правила: «аналог» на ТСЗ-1250 для «1000 кВА» показывается, хотя мощность ✗; в
карточке — «подтверждено вопреки жёсткому правилу — повод пересмотреть правило»;
- «не подходит» убирает строку, даже если правила её пропускали (воздуховод 0,55 мм на «толщина 3 мм»: толщину
правила не читают); убраны все — причина `dismissed`, «специалист отклонил»;
- «пропустить» только пишется в журнал.

**Эталон.** Новой карточке ищется ресурс КСР (83 523 строки, по `pg_trgm`), который правила прочитали в ту же
категорию и **те же значения всех hard** — «идеальная» позиция, не строка истории. Если запрос какую-то hard
не назвал или она не прочиталась — эталона нет: «воздуховод d=200» иначе получил бы фасонные изделия любой
толщины. Демо: «кабель КВВГнг-LS 7*1.5» → КСР 21.1.08.03-0520 «Кабель контрольный КВВГнг(A)-LS 7х1,5».

**Почему не графовая БД.** Связи образуют граф, но мелкий: «та же» — кластер (сама карточка), «аналог» не
транзитивен и направлен (FRLS заменяет LS, не наоборот; A→B и B→C не дают A→C), поэтому дальше одного шага
ходить нельзя — а один шаг это JOIN двух таблиц. Карточки автоматически не сливаются: ошибочное «та же»
навсегда склеило бы два кластера; слияние — ручное действие специалиста (план).

Демо: `demo/decisions.json` — 15 решений по 11 вероятным запросам задания, `decisions load` при старте Docker
(повторная загрузка ничего не меняет). Оценка (ARCHITECTURE.md, §5) карточек не использует — иначе утечка ответов в проверку;
`decisions export` выгружает карточки в формате `gold_queries.json` как контрольные примеры.

**11. Правка знаний специалистом** (`/knowledge`, `services/editor.py`). Специалист меняет у характеристики
уровень (hard / soft / info), тип сравнения, допуск по ряду, статус и пояснение к замене, у категории — слова-признаки
и слова-исключения. Правка проверяется (`domain/editing.py`: «± ступени» только при числовом ряде, допуск 0–5,
категория не остаётся без слов-признаков) и попадает в **черновик** (`knowledge_edits`, автор и причина), на
поиск не влияет. Одна правка на поле; правка, вернувшая прежнее значение, убирает себя из черновика.

- **«Проверить влияние»** — в памяти, по правилам, без модели, ~5 с: какие строки истории черновик прочитает
иначе; с какими связями золотых карточек правила расходятся до и после (какие расхождения снимет, какие
создаст); у каких контрольных запросов сменится первая строка и станет ли она верной.
- **«Опубликовать»** — черновик становится новым активным релизом (в той же транзакции правки привязываются к
нему — история «кто, что, зачем»), история разбирается заново (ответы модели по характеристикам, которые
правила по-прежнему не читают, переносятся), API пересобирает поиск, карточки получают новые ключи:
запрос карточки читается новым релизом; если две карточки прочитались одинаково — сливаются (связи
объединяются, при конфликте побеждает более позднее решение, журнал сохраняется).
- **Подсказки** — расхождения золотых карточек с активным релизом: «аналог» отвергнут жёстким правилом →
«расширить допуск до ±N» (для сравнения по ряду) или «сделать мягкой»; «не подходит», а различие только
снижает балл → «сделать жёсткой»; значение не извлекается → задача разработчику. Подсказка — кнопка
«В черновик», сама не применяется: отметка по одной строке — довод, а не правило. Пример: «аналог» на
ТСЗ-1250 для «1000 кВА» → допуск мощности ±1; проверка показывает и цену — контрольный запрос t6
(«не найдено» для 1000 кВА) начнёт находить 1250.
